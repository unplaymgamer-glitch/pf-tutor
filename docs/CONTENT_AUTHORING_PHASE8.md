## Rules per topic
- Pointers (W9-10): only `int`, `double`, `char` pointers and arrays. Print values and use the SAME address labels as in your `memory` visual; never print real addresses in `expectedOutput` (they change between runs). To show address-related output deterministically print differences (`(p + 1) - p`, `sizeof`) or compare pointers (`p == &x`).
- Strings (W11): `std::string` (`length`, `+`, `append`, `substr`, `find`, `compare`, `getline`, `at`, `[]`, `empty`, `insert`, `erase`, `replace`, `push_back`), comparison with `==`, reading with `cin >>` vs `getline` (the leftover newline trap, with `cin.ignore()`), converting with `stoi`/`to_string`. Character functions from `<cctype>`.
- Recursion (W11): every recursive example needs a base case and a recursive case spelled out; trace WITH the call stack (several frames), compare with the loop version, show infinite recursion as a mistake (do not run it; describe the stack overflow).
- Structures (W12-13): `struct` only (no classes). Member functions inside the struct are allowed in W13 as taught in the notes. `typedef`/`using` only if the notes use them. Arrays of structures are filled with initialiser lists or by `cin`.
- Files (W14): `<fstream>`; write then read in the SAME program so the output is deterministic (create `data.txt`, read it back, print it). The verifier runs each program in an empty temp folder, so files may be created freely. Always check `if (!file)`. Mention `ios::app`, `eof` loops done the right way (`while (file >> x)` / `getline`), closing files, and that the program reads from its working folder. Do not use absolute paths. When reading a file in a sample that did not create it first, create it in the same sample.
- Graphics (W15): `graphics.h` is not standard C++. Samples use WinBGIm/Turbo C++ style (as in notes 15.3-15.4). Mark EVERY such sample `"graphics": true` and leave `"expectedOutput": ""`. The verifier type-checks them against a stub header (`scripts/stubs/graphics.h`: `initgraph, closegraph, cleardevice, putpixel, line, rectangle, bar, circle, ellipse, arc, pieslice, fillellipse, setcolor, setbkcolor, setfillstyle, setlinestyle, floodfill, outtextxy, settextstyle, getmaxx, getmaxy, delay, getch` and the colour/fill constants), so use only those. Use `initgraph(&gd, &gm, (char*)"")` and `closegraph()`. Do not write `trace` for graphics samples. The lesson explains in words and with `canvas` visuals what appears on the screen; say plainly that these programs run on a school lab PC with Turbo C++/WinBGIm and that the in-page canvas is a simulation of the same calls. Coordinates: (0,0) is the top-left, x grows right, y grows DOWN, VGA is 640 x 480. Practice questions may be `mcq`, `blank`, `bug` (spot the wrong y direction etc.) and `write`; `output` questions are not possible. Any `write` answer must also type-check against the stub header (`g++ -fsyntax-only -I scripts/stubs`). Keep graphics programs to straight-line code and simple `for` loops with literal bounds (the simulator interprets exactly that subset: assignments like `int x = 50;`, `for (int x = a; x <= b; x += s) { ... }`, function calls with number/arithmetic arguments of the loop variable, string literals in `outtextxy`).
- Projects (W16): the three lessons are guidance lessons: ideas, rubric thinking, skeleton program, demo checklist. Every code sample must still compile and run (a menu-driven skeleton reading choices from `stdin`, saving to and reading from a file, arrays of structs, validation). Do not invent grading numbers: the notes give "15% of the grade" for the project; reuse only what the notes say. Quiz/practice questions can ask which concept a project idea demonstrates.
- Only use features met by that week (see the order above); mention forward references in words only.
- Exam-level samples must look like university exam questions (trace the output, find the error, complete the code, write the program).
